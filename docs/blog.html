What is MCP and why does it need fuzzing?

The Model Context Protocol (MCP) is how AI agents connect to external tools. An MCP server exposes tools like "read file", "search database", "execute query" — and any LLM agent can call them.

Here's the problem: MCP servers accept input from LLMs. LLMs can be prompt-injected. If an attacker hides a malicious payload in a document, email, or webpage, the LLM might pass it to an MCP tool as an argument.

That means every MCP server is an attack surface. I wanted to know what actually happens when you send adversarial inputs to one — not what a static policy check predicts, but what the running server does.

Microsoft released agent-governance-toolkit — but it does static policy checks. "Does this tool declaration look safe?" That's reading the label. I wanted to eat the food.

How mcp-guard works

mcp-guard is a dynamic adversarial fuzzer. It:

  1. Spawns your MCP server as a subprocess
  2. Performs the MCP handshake, enumerates all tools
  3. Reads each tool's inputSchema
  4. Generates schema-aware adversarial payloads per parameter type
  5. Fires 25–33 payloads per string parameter and classifies every response

Prompt injection"Ignore previous instructions"Instruction override

The payloads are schema-aware: a URI parameter gets SSRF payloads, a string parameter gets shell injection + overflow + prompt injection, and no-schema tools get a 24-payload mixed suite.

The classification is where honesty lives. Every response lands in one of four buckets:
  • REJECTED — the server returned an error. Good. This is what you want.
  • ACCEPTED — a normal response, no evidence of harm. Informational: the input wasn't validated, but nothing proves it did anything.
  • FINDING — accepted and the response leaked something concrete (a stack trace, /etc/passwd contents, a private key, cloud-metadata fields).
  • CRASH — the server died. A denial-of-service bug.

Those 41 ACCEPTED results all come from no-schema tools like read_graph and search_nodes. Hand read_graph the string $(whoami) and it returns the same empty graph it returns for anything — it ignores parameters it doesn't use. Nothing executed; nothing leaked.

@modelcontextprotocol/server-filesystem

$ mkdir /tmp/sandbox $ mcp-guard fuzz -- npx -y @modelcontextprotocol/server-filesystem /tmp/sandbox Tools fuzzed: 14 Payloads sent: 490 Crashes: 0 Findings: 0 Accepted: 24 Rejected: 466 VERDICT: no confirmed vulnerabilities. 24 payload(s) accepted.

466 of 490 payloads (95%) were rejected with an error — the file-operation tools validate their paths well. Run this against a fresh empty directory: the filesystem server writes during fuzzing, so the accepted count drifts upward if the target already has files.

What the results actually mean

An earlier version of this post (and the README) called these "65 findings" and tagged them CRITICAL. That was wrong, and I fixed both the tool and the writeup. A response that doesn't error is not a vulnerability — it's a server returning output. Below is what the data honestly supports.

1. "Accepted" means no validation — not command execution

Both servers accept strings like $(whoami) without rejecting them. But accepting a string is not the same as executing it. Neither server passes these arguments to a shell; they store or ignore them. The honest signal is "this tool doesn't validate its input," which is worth knowing — but it is not a shell-injection vulnerability.

2. No-schema tools silently ignore all input

list_allowed_directories and read_graph have no meaningful input parameters. They accept every payload and return their normal response. That's expected behavior for a tool that takes no input — it's why mcp-guard files these as ACCEPTED, not as findings.

3. The SSRF and overflow payloads went nowhere

Neither of these servers exposes a tool that fetches a URL, so the SSRF payloads had nothing to reach — they were ignored or rejected, never resolved. The overflow payloads (up to 1 MB) didn't crash anything. No cloud-metadata endpoint was contacted. If you see a tool with a real URL-fetching parameter, that is where SSRF probes earn their keep — but not here.

4. The one worth thinking about: stored strings

create_entities and add_observations store whatever text you give them, including "Ignore all previous instructions." That's not a vulnerability in the server — it's working as designed — but if that stored text is later fed back to an LLM, it becomes a stored prompt injection. The risk lives in the agent that reads the data back, not in the server that stored it. Worth designing around; not something mcp-guard can confirm from the server alone.

Why this matters

MCP is one of the fastest-growing protocols in AI infrastructure, and every server is an attack surface. Dynamic fuzzing tells you how a server actually behaves under hostile input — something a static declaration check can't.

But a security tool that reports 65 false "CRITICAL" findings is worse than no tool: it trains you to ignore it. The point of mcp-guard is to send real payloads and to be honest about what came back. On these two official servers, the honest answer is reassuring: solid input validation, zero crashes, zero leaks. The value is the methodology — point it at a server that does shell out or fetch URLs, and the same harness will tell you.

Static governance reads the label. Dynamic fuzzing eats the food — and reports what it tasted, not what would make a scarier headline.

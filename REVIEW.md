# REVIEW.md — judging policy for automated code review

Reader: a review bot (Kilo Code) about to judge a change, not an agent about to
make one. Build facts live in AGENTS.md; this file carries only the judging
policy. It is committed to the base branch PRs target so a branch cannot alter
the criteria it is judged by. Kept under 10,000 characters (Kilo truncates past
that, with a note in the review summary footer).

## Severity calibration

**BLOCKING** — request changes. Any of:
- Weakens a security oracle without measured evidence: scanner rules,
  fuzzer response classification (`fuzzer.py`), payload generators
  (`payloads.py`), or the red-team battery. "Simplifies" that drops coverage
  is a regression, not a cleanup.
- Reduces prompt-injection or indirect-injection (ASI01) coverage, or makes a
  probe's pass/fail depend on model behavior instead of deterministic checks.
- Adds a runtime dependency to `src/mcp_guard` (the core is zero-dep by design;
  `pyproject.toml` `dependencies` must stay empty).
- Introduces network egress, secret handling, or credential storage outside the
  documented transport layer.
- Rewrites or deletes entries in an append-only ledger (`jev/decisions.jsonl`).
  Ledgers are append-only; history is never edited.
- Report summary numbers not backed by `FuzzReport.verify_counts()`. Numbers
  are recomputed in code, never trusted (Finding B). A summary field with no
  verification path is a blocking finding.
- Disables or weakens a CI gate (lint, type check, test matrix, secret scan,
  pr-link-check) to make a PR pass.

**MAJOR** — should fix before merge, not a veto alone:
- New probes/payloads without tests asserting generation and classification.
- New report fields without a `_provenance` entry (source id, timestamp).
- Changes to default thresholds (e.g. jev escalation threshold) without a
  calibration note in the PR body.
- README/docs claims not backed by code in the same diff.

**MINOR / NIT** — never block on these. Typos, formatting, naming preferences.
Batch them in one comment, or don't raise them.

## Paths to skip or treat specially

- `jev/decisions.jsonl` — append-only telemetry ledger. Never comment on its
  content, row counts, or formatting. Judge only the writer code.
- `CHANGELOG.md` — generated by the release workflow. Flag only accidental
  hand-edits that will conflict with the generator.
- `docs/assets/` — static assets; skip unless the diff touches them directly.
- A PR that only touches these plus docs needs a light pass, not a deep one.

## Verification expected of the author (check it happened)

- CI green: `ruff check`, `mypy src/mcp_guard`, `pytest` on 3.11/3.12/3.13.
- Every PR body links its issue (`Fixes #N` / `Relates to #N`) and carries an
  `## Adversarial review` section answering the five hard questions (why
  needed, what breaks if not, simpler alternative and why not, cost, what
  would falsify it / when to delete). A missing section is MAJOR.
- For fuzzer/scanner changes: new payloads must be exercised by tests with a
  mock transport — no live network in unit tests.
- For jev router changes: every routing decision must be logged to
  `jev/decisions.jsonl`; the router routes but never judges or gates content.

## Reviewer conduct

- Judge the diff, not the author. No praise filler, no "great question" tone.
- Do not request scope expansion ("while you're here..."). One concern per PR.
- Do not ask the author to merge; humans merge, and nobody merges their own PR.
- False positives are worse than silence: an uncertain finding is a question,
  not a BLOCKING verdict. Calibrate confidence explicitly.
- Summary style: terse. Blockers first, one line each, file:line references.
  Then majors. Then stop.

## Sub-agent budget

- Diffs under ~200 lines: single pass, no sub-agents.
- Larger diffs: at most one sub-agent for test-plan or threat-model enumeration;
  the verdict stays with the primary reviewer.
- Never fan out per-file review; it produces contradictory verdicts.
